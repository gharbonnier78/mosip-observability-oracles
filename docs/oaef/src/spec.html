1 Introduction

1.1 Purpose

This document specifies the Observability and Audit Evidence Framework (OAEF): the shared layer that makes every system delivered by the programme produce traces, logs, metrics and audit events according to a common contract, collects them as evidence, and verifies them against exact oracles derived from use cases and business rules. It is the reference for designing, deploying, operating and qualifying that layer, and for every work package that must comply with it.

The framework serves three purposes with one specification:

  • Exact validation of each delivery against its contractual specification, functional and non-functional, with sealed evidence.
  • Early reports: realistic expected data allows reports and audit extracts to be designed and tested before the system exists, revealing missing data requirements.
  • Drift detection over time: data model, business rules, latency, error behaviour, signal completeness and privacy.

1.2 Scope

In scope:

  • The generic layer: instrumentation conditions, collection pipeline, storage, consumption and correlation model, independent of the business domain.
  • Its deployment as code (Infrastructure as Code and GitOps) on the development, test/qualification, in-house integration, performance and disaster-recovery platforms, across two sites (DC1, DC2).
  • The qualification layer: test executor, synthetic data, mocks, evidence collection, oracle engine, verdict classification and reporting.
  • A reference implementation on MOSIP 1.2.x for the National Identification Number (NIN) issuance journey of NIMS 2.0, including the first scenario NIN-001.

Out of scope: production monitoring service levels, end-user support processes, and the functional design of MOSIP itself.

2 System context

2.1 Problem statement and goals

In a distributed, event-driven system spanning web and mobile clients, offline registration stations, gateways, many services, message brokers, databases and two data centres, a failed test has three possible causes: a product defect, an infrastructure problem, or missing evidence. Without designed signals these cannot be told apart, and every failure becomes a manual investigation. Retrofitting signals after delivery means changing code and re-running the tests.

GoalDescription
G1Every delivery emits the signals of its contract, tagged with environment, site, test run and business keys.
G2Every scenario run produces a sealed evidence bundle and an automatic verdict against an exact oracle.
G3Every failure is classified to its probable first source and linked to an investigation view.
G4Personal data never appears in clear in signals; audit trails are immutable and access-controlled.
G5The same layer serves development, qualification, integration, performance and DR testing on both sites.

Principal use cases of the framework: UC-F1 emit signals during a journey; UC-F2 run a scenario and open its root span; UC-F3 collect and seal evidence; UC-F4 verify against the oracle and classify; UC-F5 investigate from the report; UC-F6 consult the audit trail; UC-F7 detect drift across releases.

2.5 Constraints

  • MOSIP is a third-party open-source platform: changes are made by agent extension and configuration first; code changes are minimal, documented and proposed upstream.
  • OpenTelemetry semantic conventions used here are partly at "development" stability: versions are pinned per platform release.
  • Only synthetic personal data may be used on non-production platforms [R8].
  • Registration stations operate offline for extended periods [A: up to 72 h].

2.6 Assumptions and dependencies

  • [A] Kubernetes is the runtime for MOSIP and for the framework on both sites.
  • [A] An environment configuration manager product is available and authoritative for environment identity.
  • [A] NIMS 2.0 keeps an 11-digit NIN; the oracle reads the length from configuration.
  • Dependency: ABIS vendor capability to propagate trace context through its queues (open decision D4).

3 Architecture of the generic layer

3.1 Architectural principles

IDPrincipleRationale
P1Observability firstSignals are designed with the system, because the oracle can only expect what the system can emit.
P2Standards before customOpenTelemetry, W3C Trace Context and semantic conventions wherever they exist; organisation namespace only where none exists.
P3Extend, do not forkAgent extensions and configuration rather than changes to MOSIP code.
P4Where is a resource factEnvironment and site are resource attributes stamped by the cluster collector, not request headers.
P5Privacy by designIdentifiers are hashed; PII is denied at source and at the gateway.

3.4 Runtime view

The runtime flow is drawn on draw.io page 6. Summary:

  1. Jarvis opens the ROOT span and calls the system under test with W3C traceparent and baggage.
  2. Components emit OTLP spans, logs and metrics, and write audit and business rows.
  3. The cluster collector stamps environment and site; the gateway keeps every test trace, redacts PII, derives span metrics and routes audit records to the audit tenant.
  4. After a settle window, the evidence collector queries the stores and read-only databases, builds the manifest and seals the bundle in WORM storage.
  5. The oracle engine verifies the bundle, classifies the verdict and writes the report with deep links.
  6. Investigators open Grafana on the exact trace and time window.

3.6 Multi-environment and multi-site view

Each site runs its own collection, pipeline and storage stack; evidence and audit buckets replicate from DC1 to DC2. Environment and site identity come from the environment configuration manager, are rendered into GitOps, and are enforced by the collector agent of each cluster (upsert of resource attributes). Cross-site calls appear as parent and child spans with different acme.site.name, which disaster-recovery oracles assert.

4.6 Oracle definition language

An oracle is a YAML document with sections metadata, settle, rules, api, db, notification, traces, logs, metrics, audit, nfr, verdict. Matchers: literal (typed equality), $re, $cap, $ref, $in, $gte, $lte, $exists, $golden; span relations parent, parent_ancestor, parent_kind, after, count; collection checks ordered_subsequence. Values defined by a standard are explicit; deployment-specific values are frozen from the golden run. The schema of each file type is validated in CI (OAEF-TST-03).

7 Qualification layer

7.1 Concepts

A scenario is an executable path through a use case, written in Gherkin and bound by tags to a persona (data contract), a set of prerequisites and an oracle. Each run produces an evidence bundle and a verdict.

7.2 Components

ComponentFunction
Jarvis executorResolves the target environment, checks prerequisites, opens the ROOT span with baggage, executes steps as child spans.
Data generatorProduces residents compliant with the live ID schema and the persona, deterministic by seed, unique against the gallery.
Mocks and simulatorsABIS (NO_HIT, HIT, TIMEOUT, FAILURE), SMTP/SMS with read API, relying party, WebSub subscriber — all instrumented.
Evidence collectorSettle window, queries, manifest, hashing, signature, upload.
Oracle engineMatches the oracle, computes signal-contract coverage, classifies the verdict.
ReporterPer-clause results, first source, Grafana links; export to test management.

7.3 Execution lifecycle

  1. Resolve environment and site from the environment manager; run prerequisite checks (otherwise ENV_NOT_READY).
  2. Record metric baselines; open ROOT span; execute steps.
  3. End spans; wait for the settle window (minimum [40 s], two stable polls [15 s] apart, maximum [300 s] otherwise INCONCLUSIVE).
  4. Collect traces, logs, metrics, audit, business state and context; build manifest; seal and upload.
  5. Verify functional, non-functional and signal-contract sections; classify; report; annotate Grafana.

7.4 Verdict classification

VerdictConditionOwner
PASSFunctional checks pass and signal contract 100 %—
PASS, evidence gapFunctional checks pass, a signal or audit event missingObservability
INCONCLUSIVEEvidence pipeline unhealthy or settle window exceededPlatform, then rerun
INFRAFunctional failure with infrastructure anomaly in the windowOperations
SILENT FAILUREFunctional failure without error signal at the failing stepDevelopment and observability
TEST DATA / CONFIGBusiness rejection due to reference data or partner configurationTest environment
PRODUCT BUGError span with exception, infrastructure cleanDevelopment

7.5 Reporting and investigation

The report lists, per contractual clause, the expected value, the actual value and the evidence file; it gives the probable first source and a Grafana deep link scoped to trace, time window, environment and site. Root-cause analysis then proceeds from the evidence to the relevant code: service code, test code, infrastructure as code, gateway and WAF rules, reference data, or observability configuration.

7.6 Golden-run governance

A golden run is recorded on a validated platform, reviewed by a functional owner and an observability owner, approved by pull request, and frozen into the oracle. It is re-recorded on any platform release that changes agent, semantic conventions or MOSIP version.

8 Reference implementation: MOSIP NIN issuance (NIMS 2.0)

8.1 Use case and actors

Actors: resident applicant, enrolment officer, supervisor, introducer, adjudicator, auditor; enrolment station, central platform (MOSIP), ABIS, messaging gateway, relying party. Use cases: enrol resident, capture biometrics, issue acknowledgement (RID slip), upload packet, validate packet, deduplicate identity, adjudicate possible duplicate, issue NIN and VID, activate identity and issue credential, notify resident, verify NIN, introduce child applicant, consult audit trail. Model: models/nin-usecase.puml.

8.2 Activity and rules

The activity (model models/nin-enrolment-activity.puml) runs across five lanes: resident, messaging, enrolment station, central platform and ABIS. The station captures data and biometrics, prints the RID slip and uploads the packet, queuing it while offline; the platform validates the packet, deduplicates through the ABIS, routes possible matches to adjudication, otherwise generates the NIN and VID, activates the identity, issues the credential and notifies the resident.

10 Operations

  • Governance: owners for the attribute registry, oracles, golden-run approval and the platform; change advisory for agent and convention upgrades.
